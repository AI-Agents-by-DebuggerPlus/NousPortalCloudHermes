# Промпт для Cursor IDE: переход AHCC на Hermes Agent по WebSocket (вариант C)

Скопируй весь блок ниже в Cursor как задачу для агента.

---

## ЗАДАЧА

Ты работаешь в репозитории `NousPortalCloudHermes` (Android-приложение `AndroidHermesCloudChat`, он же AHCC).

Сейчас у приложения два транспорта до Hermes:

1. **HTTP SSE** (`data/http/HermesHttpSseClient.kt`) — говорит напрямую с сырым Nous Inference API (`POST /v1/chat/completions`), с моделью, жёстко заданной в `ConnectionConfig.model` (сейчас `z-ai/glm-4.5-air`). У этого пути нет доступа к tools/агенту, поэтому голосовые сообщения (base64 внутри текста) никто не распознаёт — модель просто "видит" их как шум и придумывает случайный ответ. Это задокументировано в `Docs/Reports/AHCC-Voice-Transcription-Gap.md`.
2. **WebSocket** (`data/websocket/HermesWebSocketManager.kt`, `/v1/ws/chat`) — уже реализован как чисто событийный (push/subscription) клиент: `for (frame in this.incoming)` читает кадры по мере поступления, никаких периодических опросов (`GET`-поллинга) нет. Реконнект — экспоненциальный backoff при разрыве соединения, это не polling, его нужно оставить как есть. `HermesRequest` (кадр на отправку) уже не содержит поля `model` — значит модель для этого пути и так не диктуется клиентом.

Изначальный замысел (владельца проекта) состоял в том, чтобы AHCC разговаривал именно с **Hermes Agent** (не с голым Inference API) — то есть с сущностью, у которой есть tools (включая распознавание речи), персистентная сессия и модель, настроенная на стороне агента/Nous Portal, а не зашитая в Android-клиенте. Текущая реализация от предыдущего исполнителя (Cursor) этого не обеспечила: по умолчанию используется HTTP SSE-путь в голый Inference.

Твоя задача — довести транспорт WebSocket до продакшен-состояния как **единственного** способа связи AHCC с Hermes Agent, полностью событийного (никаких периодических опросов, только push/подписка на кадры сокета), и убрать зависимость от клиентски заданной модели.

## ЧТО НУЖНО СДЕЛАТЬ

### 1. WebSocket — единственный транспорт

- В `ConnectionConfig` (`domain/model/HermesModels.kt`) поменять дефолт `transport` на `TransportMode.WebSocket`.
- В `TransportMode.fromStorage(...)` дефолт при отсутствии/некорректном значении в preferences тоже должен быть `WebSocket`, а не `HttpSse`.
- В `HermesChatGateway` (`data/HermesChatGateway.kt`) дефолт `activeMode` — `WebSocket`.
- Реши (и обоснуй в отчёте, см. ниже), что делать с `HermesHttpSseClient`:
  - вариант 1 — полностью удалить класс и все обращения к нему (`HermesChatGateway`, DI/фабрики, настройки, `VoiceTestScreen`, любые упоминания в UI выбора транспорта);
  - вариант 2 — оставить как legacy fallback за явным флагом в настройках разработчика (по умолчанию выключен), если посчитаешь, что резкое удаление рискованно.
  - В любом случае: в **основном пользовательском UI** (экран настроек подключения, если там есть переключатель HTTP/WS) не должно остаться возможности выбрать HTTP SSE как обычный режим работы — только WebSocket. Если найдёшь такой переключатель — убери его или спрячь за dev-флагом.
- Убедись, что `HermesChatViewModel`, `VoiceTestScreen.kt` и любые другие потребители используют только `app.chatGateway` (как сейчас `VoiceTestScreen` уже делает) и не создают клиенты напрямую.
- Пройдись по всему коду на предмет скрытого поллинга (любые повторяющиеся `GET`/HTTP-запросы по таймеру к Hermes/Inference — например, попытки подгрузить историю сессии, статус и т.п.). Если такое найдётся — либо убрать, либо заменить на данные, приходящие по WS-кадрам. Если не найдётся — явно зафиксировать в отчёте, что поллинга не было и не появилось.

### 2. Модель — не диктуется клиентом

- Убедиться, что WS-кадр `HermesRequest` (`domain/model/HermesModels.kt`) и то, что реально уходит в `HermesWebSocketManager.sendMediaMessage`, **не содержит** поля `model` — сейчас это так, не сломай при рефакторинге.
- В `ConnectionConfig` поле `model` и связанный `HermesConfig.MODEL` (`config-templates/HermesConfig.android.kt.example`) пометить как относящиеся только к legacy HTTP SSE-пути (или убрать, если удаляешь HTTP SSE целиком по варианту 1 выше). В настройках приложения (если там есть поле "модель") — убрать его из основного WS-флоу, чтобы не создавалось ложное впечатление, что Android-приложение выбирает модель. Модель должна определяться конфигурацией самого Hermes Agent на сервере (`hermes model` / `config.yaml` на стороне агента), это вне зоны ответственности клиента.

### 3. Голос — через WS `attachments[]`, а не base64 в тексте

- Для `kind=voice` (и в целом любых media) отправлять запись **через поле `attachments` кадра `HermesRequest`** (`MediaAttachmentWire`, уже существует в `domain/model/MediaModels.kt`), а не только через огромный текстовый envelope `<<<AHCC_MEDIA_V1...>>>` внутри `content`/`data.content`.
  - `sendMediaMessage` в `HermesWebSocketManager` уже поддерживает `attachments`, но проверь, что `HermesChatGateway.sendMedia(...)` и вызывающий код (`HermesChatViewModel`, `VoiceTestScreen`) реально формируют и прокидывают `attachmentWires` для WS-режима, а не только `envelopeText` с зашитым в текст base64.
  - Текстовое поле (`content`/`caption`) для голоса должно содержать короткую подпись/метаданные (например: "Голосовое сообщение", длительность), но **не обязано дублировать** полный base64 — он должен идти в `attachments[].data`. Дублирование текст+attachments сейчас удваивает размер запроса без пользы.
- Обнови `Docs/Protocols/AHCC-Hermes-Media-Protocol.md`, раздел 4 (WebSocket), если меняешь формат payload — уточни, что для WS-транспорта `attachments[]` является основным способом доставки бинарных данных, а текстовый envelope в `content` — fallback/человекочитаемая часть. Если это существенное изменение контракта — рассмотри версионирование (`ahcc.media.v1` → `v2`) согласно разделу 10 того же документа; если считаешь, что можно остаться на v1 (поле `attachments` там и так было "опциональным удобством"), обоснуй это в отчёте.
- **Важно (ограничение зоны ответственности):** сам факт транскрипции голоса в текст выполняется на стороне Hermes Agent (сервер), например через tool `transcribe_audio`, который должен принять `attachments[]` из кадра и вызвать STT. Этот репозиторий содержит только Android-клиент — ты не можешь и не должен реализовывать серверную часть агента. Твоя ответственность — гарантировать, что клиент:
  1. Корректно и полностью передаёт аудио-вложение по WS в `attachments[]` согласно протоколу;
  2. Корректно принимает и проигрывает обратный голосовой ответ, если агент его пришлёт (`kind=voice`, `direction=agent_to_client`, парсинг уже есть — не сломай);
  3. Корректно показывает текстовый ответ агента (включая случай, когда агент прислал именно транскрипт голосового, а не мусор).
  - Если для тестирования у тебя нет живого Hermes Agent с настроенным `transcribe_audio` — прямо укажи это в отчёте как известное ограничение/риск, и опиши, чем локально проверил корректность отправки (например: логами кадра, что уходит в сокет, или моковым WS-сервером).

### 4. Экран "Тест голоса" (`presentation/voice/VoiceTestScreen.kt`)

- Убедись, что тестовый экран использует WS-путь (через `chatGateway`) по умолчанию и показывает реальный ответ агента как есть — без специфичной для HTTP SSE логики (например, эвристик "похоже на HTML" — если такая логика была нужна только из-за бага HTTP-пути, её можно упростить/убрать, но не убирай общую обработку ошибок).
- Критерий приёмки такой же, как в `Docs/Reports/AHCC-Voice-Transcription-Gap.md`, раздел 8: после Send в «Ответ агента» должен появляться текст (в идеале — транскрипт), а не мусор/HTML. Поскольку транскрипция — на стороне сервера, зафиксируй в отчёте, что именно клиент теперь передаёт корректно (это твоя часть контракта), а что зависит от сервера.

### 5. Не трогай / не ломай

- Логику `HeadsetButtonHub` / BT Play-жестов записи — не относится к транспорту.
- Формат `AHCC_MEDIA_V1` для фото (`image_url` multimodal path в HTTP SSE) можно оставить как есть внутри удаляемого/legacy HTTP-клиента, но для WS убедись, что фото тоже уходит через `attachments[]` по той же логике, что и голос (единообразно).
- Существующий экспоненциальный backoff-реконнект WS (`connectWithRetry`) — это ожидаемое поведение "подписки", не полли, сохрани как есть.
- Не меняй `Docs/Reports/AHCC-Voice-Transcription-Gap.md` и `Docs/Reports/AHCC-Media-Voice.md` (это исторические отчёты о найденной проблеме) — вместо этого создай новый отчёт (см. ниже).
